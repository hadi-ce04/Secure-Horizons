Threat scenario addressed

A company runs an LLM email assistant with tools (read mail, search documents, send mail and, after a change, update a supplier's bank account). Attackers plant instructions wherever the assistant reads: the user's request, an inbox email, an internal document, or a tool's own description (tool poisoning, as a malicious MCP server delivers it). Goals: exfiltrate the inbox or a secret to an outside address, or move money by changing an IBAN. The change that opens the hole looks innocuous in code review: a softened rule, a "forward promptly" line, or simply granting a tool with every security rule intact. Nobody tests the change on the real model, and annual audits cannot keep up with weekly configuration changes.

What AgentGate does

A release gate for agent configurations. It replays 16 planted attacks N times against the trusted baseline and the proposed configuration on the deployed model (Amazon Bedrock), judges every trial deterministically (outside recipient, leaked canary or sensitive tool call; no model grades a model), decides per attack family with Wilson 95% intervals against a 15% threshold (ALLOW / BLOCK / REVIEW), names the atomic change that caused a regression or flags an interaction, writes every trial, decision, override and alert to an Ed25519-signed hash chain verifiable offline, and generates an auditor-grade PDF evidence pack for any check. A scheduled monitor re-runs the suite and alerts (JSONL / webhook).

NIST CSF 2.0 functions covered

✓Govern   ✓Identify   Protect   ✓Detect   Respond   Recover

  • Govern: the gate is a documented, versioned control; REVIEW ships only through a signed, single-use override naming actor and reason.
  • Identify: change set and tool inventory per configuration, recorded with every check.
  • Detect: measured attack success per change on the real model; scheduled re-runs with staleness, config-change and drift alerts to a SIEM sink.

Known limitations

  • Pre-deployment gate on a fixed 16-attack suite in one agent domain; attacks outside the suite are not detected; no runtime interception (the monitor re-runs on a schedule).
  • Three attacks never fired on any model (hex-encoded exfiltration to a lookalike domain, base64 instruction, spaced-out token).
  • Results are model-specific: v4 breaks Llama and barely moves Nova; Claude Haiku 4.5 resisted the whole suite, where the gate adds assurance rather than detection.
  • The ledger is signed locally: it proves records were not altered afterwards, not that the key holder cannot rewrite history; a third-party anchor is the next step.
  • Synthetic inbox, documents, secret and vendor tool only; the CI workflow is written but not yet run on GitHub; 17 of the earliest evidence bundles are reconstructed and marked partial inside their PDFs.
